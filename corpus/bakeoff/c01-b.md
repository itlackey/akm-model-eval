# System Modules & User Verification Patterns

## Privilege Gate (Privileged Console)
The `/admin/features` page is wrapped in an `PrivilegeGate`, requiring a valid escalation token before rendering the module management UI.
1. **Environment Check**: The guard checks if the environment is SaaS (`env.DEPLOYMENT_TENANT_ID === CLOUD_TENANT_ID`).
2. **SaaS Behavior**: If SaaS and no valid escalation token exists, it shows an `PrivilegeModal`.
3. **Test Harness**: In `data-platform-tests`, `authenticate(page, { role: 'superadmin' })` pre-seeds tokens, allowing superadmin roles to bypass the guard automatically.

## Page Structure
- **Path**: `/admin/features`
- **Title**: `Module Management`
- **Heading**: `System Modules` inside a `Panel` component.

## UI Elements
- **Buttons**:
  - `Enable All` (secondary small, disabled while saving)
  - `Disable All` (secondary small, disabled while saving)
- **Module Cards Grid**:
  - One card per module (currently: Connectors/Warehouse/Analytics).
  - Each card contains:
    - Icon
    - `h3` with the mapped display name (`ConnectorHub` → `Integrations`, etc.)
    - Description paragraph
    - Checkbox (`role='switch'`) with `id=module.id` to toggle state.
    - Label showing `Enabled` or `Disabled` text based on `module.enabled`.
  - Cards have a `.disabled` CSS class (opacity 0.6) when the module is disabled.

## API Contracts & Data Flow
- **GET**: `/api/data-platform-modules` — Returns the list of modules.
- **PUT**: `/api/data-platform-modules/:id` — Toggles the `enabled` state for a specific module.
- **Flow**:
  1. `FeatureViewModel.loadModules()` calls `FeatureApiClient.getModules()`.
  2. The API client checks cache (`data-platform-modules`) first; if missing, fetches from `/data-platform-modules` and caches for 5 minutes.
  3. Module names are remapped via `mapFeatureNames()` before rendering (e.g., `ConnectorHub` → `Integrations`).
  4. Toggling a module updates local state and calls the API; cache is cleared on update to force refresh on next load.

## User Verification Flow (AUTH-02)
Gap AUTH-02 covers `IdentityCheckApiClient.js` (lines 38–159) and `ConsoleViewModel.svelte.js`. The verification surface has four endpoints and a multi-step login flow with identity linking.

### Client-layer Error Code Mapping (Invariant)
`IdentityCheckApiClient.verifyUser()` wraps raw HTTP status codes into structured objects **before** returning to callers:
- `404` → `{ verified: false, code: 'ACCOUNT_NOT_ELIGIBLE' }`
- `403` → `{ verified: false, code: 'ACCESS_DENIED' }`
- other error → `{ verified: false, code: 'VERIFICATION_FAILED' }`

Other mappings include:
- `linkIdentity()` maps errors to `{ linked: false, code: response.data?.code || 'LINK_FAILED' }`.
- `checkAccess()` maps errors to `{ hasAccess: false }`.
- `verifyUserByEmail()` maps errors to `{ exists: false }`.

These mappings are **client-only** — the backend returns raw status codes; the client normalizes them for UI consumption.

### SaaS-mode Gate (Non-obvious Constraint)
The entire verification flow in `ConsoleViewModel.login()` is dead code on self-install stacks (`DEPLOYMENT_TENANT_ID` mismatch). The `isAccessDenied` UI overlay requires a `@requires-cloud-flow` gate because it never fires on self-install stacks.

### Three-step Link-Retry Flow
When `verifyUser()` returns `ACCOUNT_NOT_ELIGIBLE`, the client triggers `linkIdentity()` followed by a retry of `verifyUser()`. This is an idempotent operation (already-linked identity returns success or a 409 conflict). Accept `[200, 201, 204, 409]`.

### Auth Gate Invariant
All four `/verify/*` endpoints return `403 application/json` (not HTML) without a JWT. This is a critical failure mode for unauthenticated requests.
