# Agent Dispatch Status and Orchestration Plan

This document outlines the current state of the `akm agent` dispatch integration within the workflow subsystem. It details the absence of direct integration, the strategic direction defined in the harness-agnostic orchestration plan, and the specific implementation requirements to bridge the gap.

## Current Status: No Direct Integration

The workflow subsystem currently has **no integration with `akm agent` dispatch**. A codebase audit confirms the absence of call sites for:

- `akm agent` CLI invocation from within workflow steps
- `Bun.spawn` or similar subprocess spawning for agent dispatch
- `resolveAkmInvocation` or equivalent model/harness resolution logic in the workflow layer

The only spawn-related design found is a **rejected/redesigned monitor** process (from the check-in ADR), which was deemed non-functional and superseded by the new v2 architecture.

## Strategic Direction: Harness-Agnostic Orchestration

A draft plan for a harness-agnostic orchestration engine exists at `docs/technical/akm-workflows-orchestration-plan.md`. This document supersedes Part F of `claude-code-vs-akm-workflows.md` and serves as the owner-confirmed baseline for extending akm workflows.

### Key Design Decisions

1.  **Backend-Agnostic IR**: The plan defines an intermediate representation (Workflow Plan Graph) that is backend-agnostic, with Markdown as the primary frontend.
2.  **Durable-row Resume by Default**: Runs resume from the last checkpoint by default; detaching is opt-in for long-running tasks.
3.  **Phases and Budgets**: Per-unit output schemas, abort/budget controls are specified.
4.  **Multi-Harness Execution**:
    - **Delegate to Claude Code**: akm compiles the workflow into a Claude Code `Workflow` script, hands execution to Claude Code, and Claude Code reports every unit back to akm so `workflow.db` stays the source of truth.
    - **Native (local runner)**: For AgentRuntime SDK, Codex, Copilot CLI, Pi, Aider, Gemini, Amazon Q, OpenHands, and any headless coding-agent CLI, akm executes the same definition itself — providing the Claude-Code-equivalent fan-out, schema output, phases, budget, and resume on top of akm's existing agent-execution substrate.
    - **Cloud delegate (assign + ingest)**: For cloud-only agents that can't be invoked locally, akm assigns work to them and ingests results.

## Implementation Requirements

To support multi-agent orchestration, the system must implement the following:

1.  **Build New Dispatch Logic**: Create a new orchestrator layer (`akm workflow run`) that explicitly invokes `akm agent` (or its internal API) for each step.
2.  **Format Agent Assets per Harness**: Ensure agent assets (system prompt, modelHint, toolPolicy) are properly formatted/injected per harness (agent-runtime, claude, codex, etc.) using existing builder logic (`src/integrations/harnesses/*/agent-builder.ts`).
3.  **Resolve Models via Global Alias Tiers**: Leverage existing `resolveModel()` in `src/integrations/agent/model-aliases.ts` to map generic model aliases (e.g., `opus`, `sonnet`) to concrete harness-specific model IDs.

## Credential Snapshot and Provenance Remediation

*Updated to address recent operational changes.*

The previous status assessment did not account for operation-scoped dispatch leases or post-dispatch provenance requirements. The new orchestration plan mandates:

- **Operation-Scoped Dispatch Leases**: Dispatch operations must acquire scoped leases to prevent race conditions and ensure exclusive access during critical execution phases.
- **Credential Snapshots**: Agent credentials must be snapshotted at the point of dispatch to ensure reproducibility and auditability, rather than relying on live session state.
- **Post-Dispatch Provenance Remediation**: After dispatch, the system must remediate provenance data to link the execution result back to the specific lease and credential snapshot, ensuring full traceability from workflow definition to agent output.
