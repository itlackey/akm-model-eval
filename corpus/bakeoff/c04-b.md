# Memory Inference Architecture and Telemetry Patterns

## Idempotency via LLM Caching

The `memoryInference` process in `akm improve` (and `akm-improve-quick`) is designed to be idempotent. It relies on a generic LLM-result cache (`withLlmCache` in `src/indexer/llm-cache.ts`) that wraps every inference call, short-circuiting on body hash matches and returning cached results without re-running the LLM.

**Mechanism:**
1.  The pass collects parent memories that lack the frontmatter key `inferenceProcessed: true` (or are not yet derived).
2.  For each pending parent, it computes a body hash and checks the LLM cache.
3.  If the cache contains a valid result for that hash, the inference is skipped entirely (`onCacheHit` fires, but no new memory file is written).
4.  Only when the body changes (new session content) does the LLM run, write a derived child, and mark the parent as processed.

**Observed Behavior:**
-   The `memoryInferenceActions` metric counts batch passes (always 1), not individual memories. The real throughput is in `memoryInferenceWrites`. Recent runs show 0–2 writes despite `memoryEligible: ~2006` and `memoryDerived: ~1489`, meaning ~517 parents lack the `.derived` suffix.
-   Filesystem check reveals 523 non-derived parents, of which 497 already have `inferenceProcessed: true`, leaving only ~26 truly pending.
-   The `improve_completed` events show `memoryInferenceWrites: 0` for most runs (e.g., `2030-06-10T14:32:56.306Z`).
-   Runs taking ~33ms with 0 writes confirm cache hits are dominating the workload, preventing unnecessary LLM latency.

**Impact:**
The health report's `eligible` count is misleading — most "eligible" parents are already processed or cached. The real pending pool is tiny (~26), and those are mostly hitting the cache.

**Recommended Fix:**
None required. The system is working as designed: it avoids redundant LLM calls via caching. Consider adjusting telemetry to report `pending` (truly unprocessed) instead of `eligible` for clarity.

## Telemetry Sink Pattern for Error Categorization

For functions like `compressMemoryToDerivedMemory` that return `DerivedMemoryDraft | undefined`, swallow errors inside a feature gate (`tryLlmFeature`), and cannot carry a telemetry struct of their own, add an optional mutable telemetry sink parameter.

### Implementation Details

**Telemetry Interface:**
```typescript
export interface MemoryInferTelemetry {
  htmlErrorCount?: number;
}
```

**Function Signature Update:**
```typescript
export async function compressMemoryToDerivedMemory(
  // ...
  telemetry?: MemoryInferTelemetry,
): Promise<DerivedMemoryDraft | undefined> {
  try {
    // ...
  } catch (err) {
    if (err instanceof LlmCallError && err.code === 'provider_html_error') {
      if (telemetry) telemetry.htmlErrorCount = (telemetry.htmlErrorCount ?? 0) + 1;
      warn(`memory inference: provider returned HTML instead of JSON`);
      return undefined;
    }
    // ...
  }
}
```

**Caller Pattern (`memory-inference.ts`):**
```typescript
const inferTelemetry: MemoryInferTelemetry = {};

// Pass to both call sites (cache hit and fresh LLM)
await memoryInfer.compressMemoryToDerivedMemory(
  llmConfig,
  record.body,
  signal,
  config,
  onFallback,
  inferTelemetry,
);

result.htmlErrorCount = inferTelemetry.htmlErrorCount ?? 0;
```

### Benefits
- Minimal signature change (optional param)
- Preserves existing call sites without breaking changes
- Enables distinct error categorization inside the feature gate
- Telemetry bubbles up to the pass result and health metrics

This pattern was applied to both `memory-inference.ts` and `graph-extraction.ts`.
