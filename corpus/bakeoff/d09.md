# AKM Pipeline Cadence Changes, Lint Analysis, and Consolidate Config Resolution

## Schedule Change Summary
Recent analysis reveals significant adjustments to the scheduling cadence for key AKM pipeline tasks:

### akm-improve
- **Before:** Daily at 04:00 (`0 4 * * *`)
- **After:** Hourly at :07 past (`7 * * * *`)
- **Rationale:** Consolidation merge operations were taking 20–40 seconds each on the first hourly run, compared to a normal 9 seconds. The more frequent cadence ensures the stash remains optimized between major user sessions.
- **Impact:** More frequent reflection, distillation, and consolidation cycles keep the stash continuously optimized rather than accumulating changes for a single daily batch.

### akm-extract
- **Before:** Approximately every 30 minutes (e.g., Jun 7, Jun 8)
- **After:** ~15-minute intervals starting 2030-06-10T03:45 UTC
- **Evidence:** Runs shifted from :00 and :30 marks to a pattern including :15 marks (e.g., 03:00, 03:45, 04:00, 04:15).

## Distinction: SIGTERM vs Database Locks
When troubleshooting `akm-improve-quick` failures, check the exit code:
- **Exit 143**: The process was killed by SIGTERM (typically sent by the cron harness when a process exceeds its time limit or is forcibly terminated). Example: Session at `2030-06-10T15:09:54.367Z` showed `exitCode: 143`.
- **Exit 1/SQL error**: A database lock or other internal error occurred (e.g., `SQLITE_BUSY`).

## Consolidate Config Clobber Issue and Resolution
When `incrementalSince` is missing from quick-profile consolidate config, it runs near-full-stash sweeps (528–547 memories/run) instead of incremental ones (~50–100), generating far more proposals than triage can drain.

**Observation:** The `incrementalSince` field was clobbered from the config after a rewrite. Without it, consolidate reverted to near-full-stash sweeps (528–547 memories/run instead of ~50–100), generating far more proposals than triage could drain at 10/run.

**Impact:** Proposal backlog grew from 10 to 436 over ~18 hours, causing asset output to drop and the system to appear degraded. The issue was only detected when the Discord health report showed a "DEGRADING" verdict with 5 timeouts and p95 at 14.5min.

**Resolution:** Restored `incrementalSince: "4h"` in config.json and bumped `maxAcceptsPerRun` from 10 → 25 to drain the backlog faster. Backlog cleared in ~4 hours at this rate.

## Process-Level Config Field Drop Trap
Process-level config fields (e.g., `incrementalSince`, `maxAcceptsPerRun`) are silently dropped when the full config is rewritten by tools like `akm tasks sync` or schema expansion.

**Mechanism:** When `config.json` is rewritten (via `akm tasks sync`, `akm config set`, or any code path that serializes the full config), process-level keys inside `profiles.improve.<profile>.processes.<process>` are silently dropped if they are not in the writer's known schema.

**Observed:** `incrementalSince: "4h"` set on `quick-profile.consolidate` was lost after a config rewrite. The field was present after a manual edit, absent after the next rewrite — no warning, no error. The system silently reverted to full-stash consolidation sweeps (528–547 memories/run vs the intended ~50–100), causing consolidation proposals to outpace triage drain and a 436-proposal backlog to accumulate over ~18 hours before the regression was noticed.

**Root Cause (suspected):** The config serialization path reads the in-memory config object, which may not include fields that were added directly to the JSON file but are unknown to the config schema / not round-tripped through a typed object. On rewrite, those fields vanish.

**Impact:** Silent regression in consolidation throughput and proposal backlog growth. Requires manual verification after any config-touching operation.

**Workaround:** After any `akm tasks sync` or config-touching operation, manually verify that `profiles.improve.<profile>.processes` entries still contain custom tuning fields. Recover from `~/.cache/akm/config-backups/` if needed.

**Related:** `project_akm_config_clobber_trap` (AKM memory) — documents prior occurrences (`stashDir` reset to `(temp file)`, `llm` block dropped entirely).
