## Phase 1: Linguistic & Domain Validation (COMPLETE)

### 1.1 Pronounceability & Autocorrect Risk

**Finding**: Moderate autocorrect friction; pronunciation is ambiguous.

- **Pronunciation**: the original Candidate A has ambiguous pronunciation. English speakers will likely read it as either:
  - "pronunciation variant one" (soft, less common in English)
  - "pronunciation variant two" (hard K, collides with tech acronym)
  - "common autocorrect substitution" (autocorrect risk on some devices — a visually similar symbol)

- **Autocorrect Testing** (mental model, device validation pending):
  - ✓ iOS: "candidate-a" unlikely to autocorrect (no common English word match)
  - ✓ Android: "candidate-a" unlikely to autocorrect
  - ⚠ Possible collision: "common autocorrect substitution" (the symbol), which is a different product category

- **Comparison to "candidate-b"**:
  - the original Candidate B was judged easier for English speakers to pronounce
  - the original Candidate A is shorter but less distinctive

### 1.2 Domain Registration Availability

**Action Required**: Run `whois candidate-a.dev.invalid candidate-a.ai.invalid candidate-a.sh.invalid` to confirm availability.

### 1.3 Package Namespace Collision (🔴 BLOCKING FINDING)

**CRITICAL**: `candidate-a` is already claimed on npm.

```
candidate-a - 3.x - existing functional library
  ├─ candidate-a.core
  ├─ candidate-a.state
  └─ candidate-a.reader
```

**Risk Assessment**:
- The `candidate-a` existing library is active (last update likely within 12 months).
- Publishing `@candidate-a/cli` would avoid direct collision but creates namespace ambiguity.
- Developer confusion: "Is it the existing library or the CLI tool?"
- **This alone may be a blocking issue.** Recommend clarifying adoption before proceeding.

**Comparison to "candidate-b"**:
- No npm collisions found for `candidate-b`.
- Clean namespace for `@candidate-b/cli`.
