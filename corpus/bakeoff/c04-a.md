## Overview

The `memoryInference` process in `akm-improve` compresses recent session proposals into higher-signal derived memory facts. It operates as a batch pass over the entire memory store, not per-memory.

## Idempotency Mechanism

The pass relies on a frontmatter flag to avoid re-running the LLM on already-processed content:

1. **Eligibility Filter**: The indexer scans all `.md` files under `<stashRoot>/memories/`. It excludes any file where the frontmatter contains `inferenceProcessed: true`.
2. **Batch Execution**: Eligible parents are collected into a single batch (e.g., 517 parents in one run).
3. **LLM Call**: A single LLM call processes the entire batch, returning a map of derived children.
4. **State Update**: For each successful write, the parent's frontmatter is updated with `inferenceProcessed: true`.

## Observed Behavior

- **Cache Dominance**: Runs where only ~26 parents remain pending often complete in ~33ms because they hit the LLM cache (body hash unchanged).
- **Zero-Writes Runs**: When all pending parents have already been processed in a previous run, `memoryInferenceWrites` is 0 and duration is minimal.
- **Misleading Metrics**: The health report shows `eligible: 2006` but only ~517 are "without derived". Of those, ~497 are already marked `inferenceProcessed: true`, leaving only ~26 truly pending. This explains why most runs show 0 writes despite high eligible counts.

## Recommendation

The current design is sound and idempotent. No change needed unless the goal is to reduce the "eligible" count shown in telemetry (which would require changing how `memoryEligible` is computed).
