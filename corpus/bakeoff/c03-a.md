# Consolidate LLM Profile Resolution Pattern

This pattern resolves dedicated per-process LLM configurations from user profiles, enabling lightweight model pinning (e.g., Ministral-3b) for specific tasks like memory consolidation.

## When to use
Use this pattern when you need to resolve a specific LLM configuration for a process defined in `processes.<name>` within the user's profile, rather than falling back to a global default. This is critical when a task requires a lighter-weight model or specific runtime limits that differ from the system-wide default.

## Problem Statement
Previously, `akmConsolidate` silently defaulted to `getDefaultLlmConfig(config)`, ignoring any specific model configured for the `processes.consolidate` entry in the user's profiles. This led to silent failures or performance issues when a lighter-weight LLM (e.g., Ministral-3b) was intended for consolidation, as the default configuration often used a long-context model with restrictive runtime limits.

## Solution: Profile Resolution
The consolidation pass now uses `resolveImproveProcessRunnerFromProfile` to resolve dedicated per-process LLM configurations. This function checks the user's profile for a specific entry under `processes.consolidate` and applies that configuration if present, falling back gracefully only if no specific override is found.

### Implementation Details
- **Function**: `resolveImproveProcessRunnerFromProfile`
- **Input**: The current config object and the user's profile data.
- **Logic**:
  1. Extract the target process name (e.g., `consolidate`).
  2. Look up the specific configuration in `profile.processes.<target>`.
  3. If found, use that configuration for the runner instantiation.
  4. If not found, fall back to `getDefaultLlmConfig(config)` to maintain backward compatibility.

### Example Configuration
```yaml
# User Profile (src/user-profiles/config.yaml)
processes:
  consolidate:
    model: "ministral-3b"
    context_window: 4096
    temperature: 0.7
```

## Benefits
- **Precision**: Ensures the correct model is used for specific tasks.
- **Performance**: Allows lightweight models for memory-intensive but low-complexity tasks.
- **Flexibility**: Users can override defaults without modifying core code.
