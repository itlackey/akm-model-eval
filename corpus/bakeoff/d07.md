Promotion commits to git. A per-proposal `akm proposal revert` exists (`revertProposal`/`akmProposalRevert`, restoring the backup `promoteProposal` captures at promotion time), but there is **no batch revert**. This means a wrong bulk drain must be undone one ID at a time. Hard data-safety guardrails are enforced via `--max-accepts`, `--dry-run`, and `--yes` flags to prevent accidental mass promotions.

The `akm improve` command now performs end-of-run auto-sync for git-backed stashes. This behavior is gated on three conditions: (1) the run is not a dry-run, (2) the primary stash directory contains a `.git` folder (detected by checking for existence), and (3) the sync override flags (`--sync/--no-sync`) do not explicitly disable it.

When these conditions are met, the command calls `saveGitStash` with the configured sync message template (which supports `{token}` placeholders like `{timestamp}`, `{ref}`, etc.). The result is recorded in the `AkmImproveResult` interface under a new `sync` field: `{ committed: boolean; pushed: boolean; skipped: boolean; reason?: string }`. A corresponding `stash_synced` audit event is logged to `state.db`.

The sync outcome is non-fatal: if `saveGitStash` fails (e.g., due to permission issues or a detached HEAD), the run continues and reports `skipped: true` with an optional reason. The CLI also supports `--push/--no-push` flags to control whether the commit is pushed to the remote after the sync.

This behavior replaces the previous model where per-asset commits might have been made at boundaries; now a unified batch commit occurs at the end of the improve run.

## Recognition Pattern

When determining whether a stash directory should be treated as `git-backed`, check for the existence of a `.git` subdirectory:

```typescript
export function isGitBackedStash(stashDir: string): boolean {
  return fs.existsSync(path.join(stashDir, ".git"));
}
```

This pattern is used in `src/sources/providers/git.ts` and decoupled from the per-write commit path.

## Why This Matters

- `akm init` git-inits the primary stash (see `init.ts:96 ensureGitRepo`), so a freshly-initialized local stash with no remote is still recognized as git-backed.
- Recognition is used to gate end-of-run batch commits via `saveGitStash`, not per-asset writes.
- The inline check in `saveGitStash` now calls this helper for consistency.

## Change: Repo Directory Override and Global Locking

Updates to the Git stash management system include an optional `repoDir` parameter for `saveGitStash` to prevent directory divergence and a global `improve.lock` file scoped to the primary stash directory to serialize concurrent maintenance tasks.

### Added Parameter
Added `options?.repoDir?: string` parameter to `src/sources/providers/git.ts`'s `saveGitStash` function. Callers that have already resolved the primary stash directory (e.g., `akm improve`'s end-of-run sync) can now pass it directly:

```typescript
const syncResult = saveGitStashFn(
  undefined,
  message,
  writableOverride,
  { push, repoDir: primaryStashDir }
);
```

This ensures the pre-commit gate (which validated `primaryStashDir`) and the commit operation target the **same** directory, avoiding divergence when a caller passes a non-default `stashDir`.

### Locking Mechanism
The locking mechanism in `src/commands/improve.ts` (lines 860-920) uses a single lock file path derived from `primaryStashDir` (or `stashDir`) at `path.join(primaryStashDir ?? options.stashDir, '.akm', 'improve.lock')`. The logic explicitly checks for stale locks across the entire primary stash before allowing a new run to proceed and handles stale locks with a 4-hour grace period (`MAX_LOCK_AGE_MS = 4h`), emitting `improve_lock_recovered` events for audit trails.

The lock is acquired before the main loop and released after cleanup/reindex operations. It protects the entire run, including all phases and the post-loop backlog drain. If a process like 'triage' were to be run independently or in parallel without respecting this global lock scope, it could corrupt the queue state. Any cross-cutting maintenance task (like a proposed 'triage' process or backlog drain) must respect this same lock scope.

## Architectural Note

The primary stash stays `kind: "filesystem"` on purpose during asset writes. Routing every write through `runGitCommit` would be incomplete (stages only the single asset file, leaving `.akm/proposals` + other state dirty) and noisy (~25 commits per run). Recognition is used only to gate the end-of-run BATCH commit.

## Benefit

Eliminates redundant `resolveStashDir()` calls and prevents subtle bugs where validation and execution operate on different directories. Additionally, the global lock prevents race conditions where multiple processes try to read/write the shared proposal queue simultaneously, ensuring that concurrent runs of `akm improve` against different scopes or sub-agents are mutually exclusive if they share the same `primaryStashDir`.

**Implication:** This means concurrent runs of `akm improve` against different scopes or sub-agents are mutually exclusive if they share the same `primaryStashDir`. The lock is not granular per-ref or per-subagent; it is a global guard for the entire improvement pipeline. This prevents race conditions where multiple processes try to read/write the shared proposal queue simultaneously, but it also means that a long-running 'triage' process would block all other improvement activities on that stash until completion.

**Architecture Implication:** New processes cannot assume they can operate outside the primary stash directory's `.akm/improve.lock` boundary. If a process needs to drain the proposal queue, it must either:
1. Acquire the same lock (risking serialization with the main loop), or
2. Be designed as a cross-cutting maintenance step that runs after the main loop releases the lock.

This constraint was verified by inspecting the lock acquisition logic and its integration with the reindex workflow (lines 860-920, 1468).
